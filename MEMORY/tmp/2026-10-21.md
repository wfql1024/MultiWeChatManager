## 22:46:31 — 补丁系统动工：缓存构建器 + 修掉扫描恒失败的移植 bug

- 做了什么 / 结论：
  - 新增 `swcore/SwPatchCacheBuilder`：把远程配置的 `features`/`patch_rules` 扫描成物化偏移，写入 `SwCache.json` 的
    `{mode}.channels.{ch}.precise_ver_adaptations.{ver}`。三条闸门按 Python 原样实现：
    没有任何规则产出列表 → 删该版本缓存（DISABLED）；任一失败 → 不写缓存（FAILED）；全成功 → 写（OK）；缓存合法 → SKIPPED。
  - 缓存条目结构扩展为 `{addr, dst, kind, wildcard, del, patches[]}`：`addr` 是源绝对路径、`dst` 是刷入目标（含 `?`）、
    `kind` 区分 file/dir；顶层 `dst = 源目录 + wildcard`，nested 子项按父级 `src/dst` 拼接。
  - 目录 feature（`addr` 以 `/` 结尾）不扫特征码，只产出复制条目，`nested` 递归处理子项。
  - 缓存键名统一为 `precise_ver_adaptations`（与远程配置一致），读取兼容旧的 `precises`。
  - `SwAdapterChecker.identifyDllCore` 接上缓存构建（主程序按 `forceRescan` 决定 skip，共存实例一律允许跳过），
    新增 `SwPatchCacheBuilder.setForceRescan/isForceRescan`。
- 为什么 / 证据：
  - **发现并修掉一个移植遗留的真 bug**：`SwHexUtils.searchPatternDicts` 用 `aligned.size() != 2` 判断对齐结果，
    但 `convertAndAlign` 返回的是 token 列表（长度＝特征码字节数）→ 恒失败，扫描从来没成功过。
    这是整个补丁功能在 Java 侧一直不可用的根因（缓存永远是空的）。
  - 另一个小坑：缓存条目组装时把 feature 的原始 `addr` 又覆盖回解析后的地址，导致目录条目带尾斜杠、与 `dst` 不一致。

    全部弃用删缓存 / 目录+nested 拼接 / 真实文件特征码回归）。测试用临时目录 + 复制的系统 exe（带版本信息）跑真实扫描。

  lessons（"对齐函数的返回值语义被误判 → 扫描恒失败"、"组装缓存条目时不要把源字段覆盖回原值"）
